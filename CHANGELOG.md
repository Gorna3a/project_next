All notable changes to the PixelCode product are documented here.

### Added
- Pixelact UI (shadcn registry) compatibility — nothing installed yet, but
  the plumbing is in place so components drop in cleanly. OpenCode
  `opencode.json` registers the shadcn MCP server (`npx shadcn@latest mcp`,
  local); `components.json` registers the `@pixelact-ui` registry (install
  any time with `npx shadcn@latest add @pixelact-ui/<name>`, e.g.
  `button`, `dialog`, `kbd`, `card` — tailwind + lucide consistent);
  `src/lib/utils.ts` exports `cn()`; `tailwind.config.js` maps the shadcn
  semantic colors (`border`, `background`, `foreground`, `card`, `popover`,
  `primary`, `secondary`, `muted`, `accent`, `destructive`, `ring`) onto
  the pixel shell tokens, so registry components render correctly in both
  LIGHT and DARK without touching `globals.css`.
- **Server-authoritative XP system** (`POST /api/xp/award` +
  `firebase-admin`). XP is no longer written by clients anywhere — all
  awards are committed by the server in one transaction, with per-user
  idempotency ledgers in a new `xpEvents` collection (doc id =
  `<uid>_<action>_<key>`), so re-solving a lesson/quiz/challenge or
  re-finishing a duel never double-pays. Awards: lesson completion
  (+10, first time only), quiz correctness (award only on first-time
  correct answers), challenge completion (+`challenges.xp`, read
  server-side — the client-sent value is never trusted), revealed
  solutions (0 XP, completion recorded with `revealed: true`), duel
  finish (first to finish wins `challenge.xp`; the other player gets a
  fixed +10 consolation), and a +100 course-completion bonus the first
  time `percentComplete` reaches 100. `level = floor(xp/1000) + 1` is
  recomputed server-side. The client can only *request* an award with
  its Firebase ID token (`Authorization: Bearer`); unauthenticated calls
  get 401. New `.env.local` / Vercel var: `FIREBASE_SERVICE_ACCOUNT_B64`
  (base64 of the Admin service-account JSON — server-only).
- **Daily streaks now actually work**, server-side, for every XP-earning
  action: same day → unchanged, yesterday → +1, older/missing → reset to
  1. `lastStreakDate` (YYYY-MM-DD) is stored on the user doc; the client
  proposes its local date (validated; future dates rejected, UTC used as
  fallback). A one-off `scripts/backfill-streaks.mjs` reconstructs runs
  from timestamped activity (courseProgress `startedAt`/`lastAccessed` +
  `completedChallenges.completedAt`). Dry run on production showed
  historical daily activity was never logged — only challenge completions
  and course touches exist — so reconstruction yields ≈ 1-day runs for
  past users, which is why it was **not** applied; streaks repair
  themselves going forward. XP was never touched by the backfill.
- **Firestore rules v2** (`firestore.rules`, requires
  `firebase deploy --only firestore:rules` to take effect): clients may
  no longer write `totalXP`, `level`, `streak`, `lastStreakDate`, or
  `lastActive` at all — the whitelisted owner-update keys are
  `displayName, photoURL, photoSource, preferences, lastActive`;
  `courseProgress`, `completedChallenges` and `xpEvents` are fully
  server-write-only (owner read preserved for progress); 
  `competitive_leaderboard` is read-only for clients (server updates it
  in the same transaction); `duel_rooms` clients may only flip their own
  `creatorStatus`/`opponentStatus` (plus the pre-existing join
  transition) — **`winnerId` and `status: 'finished'` are no longer
  settable by clients**, so a losing player can no longer crown
  themselves winner.
- **Google/GitHub profile pictures sync automatically**: on every login
  (`finalizeAuth`), the OAuth provider's `photoURL` is copied into the
  profile when it differs — unless the user deliberately picked a
  platform avatar (`photoSource: 'platform'`) or uploaded one
  (`'upload'`). `photoSource` is tracked on the user doc
  (`google` | `github` | `email` | `platform` | `upload`).

### Fixed
- Friend request accept crashed with `Function setDoc() called with invalid
  data. Unsupported field value: undefined (found in document
  friendships/…)`. Root cause: Firestore rejects `undefined` anywhere in a
  document — any profile with no Google picture (or any legacy bell
  notification created before payloads were sanitized) produced undefined
  values that leaked into `friend_requests` / `notifications` /
  `friendships`. `socialService` now deep-strips `undefined` from every
  payload before writing (keys dropped, array items → null, FieldValue
  sentinels preserved), validates uids up-front (`requireUid`), the
  NotificationTray auto-detects and deletes corrupt legacy entries instead
  of writing a garbage `friendships` doc, and `handleAcceptFriend` re-checks
  the sender uid before calling the accept path.
